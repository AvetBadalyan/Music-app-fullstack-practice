# Refactor drops service-level DB error wrapping; the rest is CRLF line-ending churn

The diff looks enormous (35 files, ~1,500 lines each side) but that is almost
entirely a red herring: the agent rewrote every file with CRLF line endings
while HEAD uses LF, so 30 of 35 files are byte-identical once end-of-line
differences are ignored. Only five files carry real content changes, and four of
those change the same one thing — the `try/catch` blocks that wrapped raw
database failures into a `DatabaseError` were removed from every method in
`album`, `artist`, `genre`, and `song` services. The fifth change is an
improvement to the error-handler's server-side logging. No controller, entity,
DTO, middleware (including `requireAdmin`, `fileUpload`, `validateRequest`),
CORS config, or seed logic changed at all.

Watch for: (1) removing the service `try/catch` changes the **client-facing
error message** on DB failures — 500 status is preserved, but in production the
body flips from a friendly `"Failed to create album"` to the generic
`"An unexpected error occurred!"`, and in development it now leaks the raw
Postgres/TypeORM message (confirmed). (2) The whole-repo CRLF conversion shows
up as a massive, unreviewable diff on commit and buries the two real changes
(confirmed). Neither is a correctness bug, but both are things the original
approving team lead would notice.

**Verdict**: NEEDS_CHANGES

## High-level view

The architectural pattern is untouched. The class-based controller-calls-service
pattern, the `NotFoundError` → 404 flow, the `next(error)` → central
`errorHandler` chain, DB query semantics (relations, selects, cascade deletes),
status codes, and response shapes are all identical to the approved version. The
React frontend's API contract is preserved: same routes, same JSON shapes, same
success codes, same 404 behavior. No new abstractions or layers were introduced
— the refactor only deletes code, so there is no over-engineering to flag.

The one real behavioral shift is error translation. Previously each service
method caught unknown errors and rethrew them as `DatabaseError` (status 500,
fixed message) while re-throwing known errors like `NotFoundError` untouched.
The refactor deletes those wrappers everywhere. The HTTP status for a DB failure
is still 500, so status-based frontend handling is unaffected; what changes is
the message the client sees, in opposite directions for dev vs prod — a
raw-error leak in dev, a less specific message in prod.

The error-handler change is worth keeping: unexpected (non-`CustomError`)
failures now log the full error object with stack, the only record left since
the production response deliberately hides the cause.

The dominant issue by line count — the CRLF conversion — is not a behavior
change but a process problem. With no `.gitattributes` and `core.autocrlf`
unset, committing this makes every file look 100% rewritten, destroys
`git blame`, and hides the two substantive changes from any reviewer.

<summary>Details</summary>

### The diff is 97% line-ending conversion

`git diff HEAD --stat` reports 35 files and ~3,100 changed lines.
`git diff HEAD --ignore-cr-at-eol --stat` reports 5 files and 613 lines. The gap
is entirely CRLF: HEAD stores every file with LF (`file` reports "ASCII text"),
the working tree stores them with CRLF ("with CRLF line terminators"). There is
no `.gitattributes` and `core.autocrlf` is unset, so nothing normalizes this on
the way in.

The damage is reviewability, not runtime. `src/controllers/*`, `src/entities/*`,
`src/dto/*`, `src/middlewares/*` (including `requireAdmin`, `fileUpload`,
`validateRequest`), `src/routes/*`, `src/types/*`, `src/seed/seed.ts`,
`src/app.ts`, `src/data-source.ts`, and `src/services/supabaseStorage.ts` are
all zero-change once EOL is ignored (verified per-file). Committing as-is means
auth enforcement, CORS, upload handling, entity relations/cascades, and
validation rules all appear rewritten when none of them moved. Normalize the
untouched files back to LF and land only the two real edits; a repo-level
`.gitattributes` with `* text=auto eol=lf` prevents a repeat.

### Service error wrapping removed across all four services

Every method in `AlbumService`, `ArtistService`, `GenreService`, and
`SongService` shed the same shape:

```ts
try {
	// ... query / save / delete ...
} catch (error) {
	if (error instanceof CustomError) throw error // preserve NotFoundError etc.
	throw new DatabaseError('Failed to <op>') // wrap raw DB failures -> 500
}
```

`NotFoundError` is still thrown directly inside the method bodies, so 404
behavior is fully preserved — the removed catch only ever re-threw those
untouched. The behavioral delta is confined to _unexpected_ failures (a dropped
connection, a constraint violation, a TypeORM `QueryFailedError`).

Tracing an unexpected DB failure through the unchanged controller
(`next(error)`) and the `errorHandler`:

```
                        old (DatabaseError, isKnownError=true)   new (raw Error, isKnownError=false)
status code             500                                      500                       (same)
prod response body      "Failed to create album"                "An unexpected error occurred!"   (changed)
dev response body       "Failed to create album"                <raw Postgres/TypeORM message>    (changed)
```

The message differs in both environments, in opposite directions: production
loses the operation-specific hint, development gains a raw DB string in the HTTP
body. The dev leak is dev-only but is a real information-exposure change from
the approved version. Whether it matters depends on whether those
`'Failed to <op>'` messages were a deliberate part of the contract the team lead
signed off on, or incidental — a call the author should make consciously rather
than by deletion.

### Error-handler logging is now failure-aware (keep this)

```ts
if (isKnownError) {
	console.error(`${err.name}: ${err.message}`) // deliberate 404/400 -> one line
} else {
	console.error(err) // unexpected -> full object + stack
}
```

Previously every error logged a single `name: message` line without a stack.
Since the production response intentionally hides the cause of unexpected
errors, that line was the only server-side record. Logging the full error object
for the non-`CustomError` branch restores the stack for exactly the cases where
it matters, and makes the removed
`console.error('SERVICE CREATE FAILED:', error)` in `song.create` redundant
rather than a regression.

### Not tested

There is no test suite in the repo (`src` has no `*.test.ts`/`*.spec.ts`, and
`package.json` has no `test` script). The error-message behavior change on DB
failures is unverified by any automated check; it was traced by reading
`errorHandler`, `errors.ts`, and the controllers. `npx tsc --noEmit` passes, so
the deletions leave no dangling imports (`DatabaseError` is still used in
`app.ts`).
